Six assertions worth naming, because each one guards a bug that was actually shipped and caught:

- **The Windows installer, executed.** Three consecutive failures on a real Windows 11 machine were found by
  the user and none by this suite, because nothing here could execute batch — and all three were the same
  root cause, `cmd.exe` mis-parsing a nested block, which it does without printing anything. The installer is
  PowerShell now and `pwsh` runs on macOS, so 13 of the checks above are runs rather than readings: a full
  install into a fresh temp `HOME`, the updater over its result, and refusals for a non-empty target, an
  unresolvable URL, missing Git under `-SkipDeps`, Node.js 16, and no-console consent. Running the code
  immediately surfaced two defects that reviewing it had not — an unwritable log path that threw, and a
  `catch` block that then threw while reporting it, destroying the original message. The `.cmd` files that
  remain are launchers with no branching, and a check holds them to that.

- **A full install, end to end, over `file://`.** The suite had no check that ever ran `git clone`, and a
  defect that made *every* fresh install fail on both platforms shipped through it — see
  [Installer defects found after WU-17](#installer-defects-found-after-wu-17). The check builds a fake remote
  from this checkout's tracked working-tree files and installs from it into a fresh temp `HOME`. It is built
  from the working tree, not by `git clone --bare`, because a bare clone ships `HEAD` and would test the last
  commit rather than the change in front of the author. Confirmed to go red when the log-placement fix is
  reverted.

- **`claude --plugin-dir` actually lists them.** `claude plugin validate` passes on a plugin whose skills do
  not resolve. Only loading the plugin proves discovery works.
- **Over-limit portal fails loudly.** Not "the bundle is within limits" — the opposite assertion. It drives
  the real limit path via `--limits` with a shrunken threshold and asserts the tool exits non-zero *and*
  prints no success marker. An earlier version of this test passed because an invented portal name failed
  argument validation before any limit was consulted.
- **Line endings as *stored*, not as delivered on checkout.** This assertion used to be backwards: it
  required the committed blob to be LF-normalised and trusted `eol=crlf` to repair it during checkout. Nobody
  who double-clicks an installer performs a checkout — they download the raw file, which is served byte for
  byte, and cmd mis-parses LF-only blocks in silence. The check now walks every `*.cmd`, `*.ps1`, `*.command`
  and `*.sh` and asserts the stored bytes are what the interpreter needs, counting *lone* LFs rather than CRs
  so a mixed-ending file cannot pass. It is paired with an assertion that `*.cmd` is `-text`, since that is
  what makes the stored bytes authoritative.
- **The prerequisite checks carry their own control.** A missing tool is simulated with a stub on `PATH` that
  exits non-zero, and the Homebrew probe paths are neutralised so `brew shellenv` cannot put the real tool
  back in front of the stub. A fourth check runs the identical setup *without* the stubs and asserts both
  tools are accepted — otherwise "`--skip-deps` refuses" and "no console declines" would pass just as
  happily if the installer were failing for some unrelated reason. Both were confirmed to go red when the
  stub is removed.

## Prerequisite installation (WU-17)

The installers install Node.js and Git themselves rather than opening a download page. This is the one area
where verification is asymmetric, so it is recorded separately rather than folded into the table above.

**Verified by execution on macOS.** Not by reading — each of these was run:

| What | How it was proven |
|---|---|
| Missing-Node detection | A copy of the installer with the Homebrew probe paths redirected to `/nonexistent`, run under a stripped `PATH`, so all three branches (brew present, brew absent, tool already present) were exercised separately |
| LTS version discovery | `nodejs.org/dist/index.tab` parsed with `awk`; column 10 is the LTS name and `-` when not LTS. Confirmed against the live file |
| Real `.pkg` install | A genuine ~90 MB download with `sudo` stubbed out, so the download, checksum, and install invocation all ran without touching the machine |
| Checksum verification | The downloaded package was deliberately corrupted; the installer refused to install it and said the checksum did not match. A guard that has never been made to fire is not a verified guard |
| Command Line Tools label parsing | The `softwareupdate -l` pipeline was run and checked to be safe under `set -euo pipefail` — a non-matching `grep` in a pipeline is the classic way these scripts die silently |
| Homebrew `PATH` inheritance | Confirmed that `brew shellenv` loaded by absolute path is what makes a double-clicked `.command` see an Apple-silicon Homebrew at all |

**Windows: the installer's own logic is verified by execution; the OS-specific parts are not.** The batch
installer was run on a real Windows 11 machine by the user and failed three times — always on `cmd.exe`
mis-parsing a nested block, silently. It was rewritten in PowerShell, which changed what can be tested
here: `pwsh` runs on macOS, so the full install, the updater, and the refusal paths are now executed on
every `npm test`, and the prerequisite-detection logic (missing Git, Node.js 16) runs against stubs the same
way the macOS installer's does.

What is still **never executed on Windows** is the part that only exists on Windows: the winget branch, the
Node.js `.msi` install and its `Get-FileHash` verification, the derivation of the Git for Windows asset name
from the `/releases/latest` redirect, UAC elevation, and the double-click launcher path through
`powershell.exe -ExecutionPolicy Bypass`. Those were cross-checked against live URL probes and reviewed, but
reviewing is not running. Manual cells 7.3–7.6 exist specifically for them and are marked UNVERIFIED.
**A sign-off that skips them does not cover Windows prerequisite installation.** The PowerShell installer
has not yet been run on a Windows machine at all.

## Installer defects found after WU-17

Three defects were found by a user on Windows 11 after WU-17 was reported complete. They are recorded here
because of what they say about the coverage, not just the code.

| Defect | Effect | Where it lived |
|---|---|---|
| The log file was written into the clone target | `git clone` refuses a non-empty destination, so **no fresh install could succeed** | Both platforms |
| `.git` appended on every validation call → `edwin.git.git.git` | Clone failed on a mangled URL; the `owner/repo` shorthand never matched either | Windows only |
| `package.json` URL split on `:` | Yielded `git+https` instead of the URL | Windows only |

The first is the one worth dwelling on. It was a **total** failure of the installer's main path, on both
platforms, and it shipped. Two things let it through:

- **No automated check ever ran `git clone`.** Every installer check tested a path that *refuses* — help,
  argument validation, `--skip-deps`, the no-console decline. All of them passed, on code that could not
  install anything. Coverage that only exercises refusals cannot see a broken success path.
- **The emptiness check exempted `install.log`.** The installer was asked whether the target was empty and
  answered "yes, apart from the file I just put there." `git` was not consulted, and `git` disagreed. An
  exemption written to make a check pass is worth more suspicion than a check that fails.

The `.git.git.git` defect has a narrower lesson: `echo %VAR% | findstr "pattern$"` can never match in cmd,
because `echo` emits the space that sits before the pipe. The suffix test had been read and reviewed several
times without anyone noticing, which is roughly what "reviewed but never executed" is worth on a shell
dialect nobody was running.

Both are now covered by the end-to-end install check.

### The fourth failure, and why the installer is PowerShell

Two further Windows runs failed after those fixes: one where the installer produced no output at all beyond
its first few lines, and one where the window closed with nothing on screen and a log that stopped mid-step.
Both were `cmd.exe` mis-parsing a nested `if (...) else (...)` block — it skips the inner lines and continues
somewhere unintended, or aborts the shell with a message that flashes past as the window closes. The
specific trigger in the last case was a `for /f ... in ('cmd 2^>nul')` inside a block, where one caret does
not survive two rounds of parsing, so the redirection lands on the `for` statement instead.

The pattern across all five failures matters more than any of them: **every one was found by the user, none
by this suite**, because nothing on a Mac can execute batch. Static analysis of the dialect was tried and
abandoned — one proposed lint could not be made to go red against the very bug it claimed to guard, which
made it decoration rather than a test.

So the language changed. `EDWIN-Install.ps1` and `EDWIN-Update.ps1` replace ~1,200 lines of batch;
PowerShell 5.1 ships with every supported Windows, and `pwsh` runs here, so the installer moved from
*reviewable* to *executable*. The first execution found two defects immediately — a log path whose parent
directory did not exist, and a `catch` that threw while reporting the failure, destroying the original
message. Neither was visible by reading. What remains in batch is two launchers, 40 and 33 lines, with no
branching at all, and a check asserts they stay that way.

## Fictional-user sweep

- `git grep -inE 'derik|hammer|sqlhammer|C:\\repos|/Users/[a-z]'` finds nothing outside `specs/` and
  `docs/testing/` except the project's own canonical remote, which conventions §11 permits in install
  instructions. The automated audit enforces this per-line rather than by exempting whole files: a line
  containing the account name is allowed only if it also contains `github.com/<owner>/edwin` or
  `github:<owner>/edwin`. The one non-URL exception is `.claude-plugin/marketplace.json`, whose schema
  requires `owner.name` to be the hosting account.

- `tools/validate/denylist.txt` ships with commented placeholders only, so the file itself stays portable.
  A user adds their own patterns; nothing personal is baked in.
