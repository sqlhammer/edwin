# EDWIN v0.2 Conventions

**This document is the contract.** Every work unit, every dev agent, and every skill — hand-written or
generated by EDWIN's own meta-skills — conforms to what is written here. When a spec and this document
disagree, raise it rather than guessing.

Framework version lives in [core/VERSION](../core/VERSION). Current: `0.2.0-dev`.

## 2. The three laws

These override everything else in this document.

1. **Markdown-first.** No feature may *require* code to function. Skills are instructions; scripts are
   accelerators the AI invokes when it has shell access. If a skill cannot do its job by instructing the
   model to use ordinary file tools, the skill is designed wrong. See §6.
2. **Portability.** Nothing user-specific ever lands in `core/`, `tools/`, `docs/`, `specs/`, or the
   generated `CLAUDE.md`. No real names, no home directory paths, no account handles, no company names,
   no repository owners. Personal data lives only in `user/`. Examples use fictional people —
   **Alex** (Windows) and **Sam** (macOS) are the canonical stand-ins.
3. **Hyper-concise by default.** EDWIN answers what was asked and stops. See §5 — it binds every line of
   skill dialogue, every example transcript, and every prompt EDWIN is instructed to emit.

## 3. Skill format

One skill per directory: `core/skills/<kebab-case-name>/SKILL.md`. The directory name **must** equal the
frontmatter `name`. Additional files may live alongside (`reference/`, `scripts/`, `assets/`); they are
copied verbatim on install.

### 3.1 Frontmatter

YAML, fenced by `---`, first thing in the file. No tabs. No anchors, aliases, or multi-document markers —
the vendored parser in `edwin-doctor` supports scalars, block strings, and flow/block sequences only.

```yaml
---
name: invoice-tracker
description: Tracks outstanding client invoices and drafts follow-up messages. Use when the user
  mentions unpaid invoices, chasing payment, accounts receivable, or asks who owes them money.
contexts: [Work]
version: 1.0.0
requires: []
author: edwin-core
---
```

| Key | Required | Type | Rules |
|---|---|---|---|
| `name` | yes | string | kebab-case, `^[a-z0-9]+(-[a-z0-9]+)*$`, matches the folder name. Framework skills are prefixed `edwin-`. |
| `description` | yes | string | **One paragraph, trigger-optimised.** Sentence one: what it does. Sentence two: *when to use it*, naming the words and situations a user would actually say. 2–4 sentences, ≤ 500 characters. Written in the third person about the skill, never "I". This string is the only thing the harness sees when deciding to route — it does the work. |
| `contexts` | yes | list or `all` | Each entry must be a context `name` in `contexts.json`, or the literal string `all`. `all` means the skill is context-neutral and appears in every listing. Use a flow sequence (`[Work, Home]`) or `all`. |
| `version` | yes | string | Semver, per skill, independent of the framework. Migrated v0.1 skills start at `1.0.0`. |
| `requires` | yes | list | Optional capabilities the skill *prefers*: `shell`, `web-search`, `web-fetch`, or a script path relative to the repo root (`tools/memory/memory.mjs`). Empty list `[]` means pure-instruction. Never a hard dependency — see §6. |
| `author` | yes | string | `edwin-core` for shipped skills; `user` for skills EDWIN generates for its owner. |
| `type` | no | string | `persona` for persona-mode skills (WU-11). Omit for ordinary skills. Persona skills are listed separately. |
| `keywords` | no | list | Extra routing hints. Rarely needed — a good `description` is better. |

### 3.2 Body

Sections in this order. Headings are exactly as written (`##`), so tooling can find them.

```markdown
# <Human Readable Name>

## Purpose
One or two sentences. What problem this solves for the user.

## When to use
Bulleted triggers in the user's own words ("chase that invoice", "who hasn't paid me").
Include a short "Not for" list when the skill is easily confused with a neighbour.

## Instructions
The actual methodology, numbered. This is the bulk of the skill. Write imperatives addressed to
EDWIN ("Ask for the client name before searching"), not descriptions of behaviour.
Mark user-facing dialogue with > blockquotes so the conciseness rule is auditable.

## Optional script hooks
Table of script, purpose, and invocation. Omit the section entirely if `requires: []`.

## Degradation
REQUIRED. What this skill does when its scripts, shell, or harness features are unavailable.
One row per capability. See §6.

## Examples
One or two compact transcripts using Alex or Sam. Conciseness rule applies — examples that show
EDWIN monologuing are bugs.
```

`## Degradation` and `## Examples` are mandatory; `edwin-doctor` fails a skill that lacks either.

### 3.3 Size budget

A `SKILL.md` over ~250 lines should push its detail into a sibling `reference/` file and point at it.
Skill bodies are loaded on demand, so this is a soft limit — but web-portal bundles (WU-13) flatten skill
bodies into a character-limited instruction blob, and fat skills are the first thing truncated.

## 4. Persona format

`core/persona/*.md` are plain markdown with no frontmatter. The sync engine concatenates them, in this
order, into the managed block of the installed `CLAUDE.md`:

1. `identity.md`
2. `operating-rules.md`
3. `harness-detection.md`
4. `hooks/*.md`, sorted by filename

**Combined budget: 300 lines.** `edwin-doctor` warns past it and fails past 400. Persona text rides in
every single context window; every line costs the user money forever. Ruthlessness is the correct posture.

### 4.1 The hooks directory

A hook is an **always-on behaviour** that a skill needs EDWIN to exhibit *before* that skill is invoked —
noticing things. Memory capture (WU-17), win detection (WU-18), and repeated-workflow observation (WU-09)
are hooks: they must fire unprompted, so they cannot live inside a skill body that is only read after
routing.

File: `core/persona/hooks/<hook-name>.md`. Format:

```markdown
### Hook: <name>
**Owner skill:** <skill-name>
**Fires when:** <one line>

<3–12 lines of instruction. Hard ceiling: 15 lines.>
```

Rules:
- One hook file per owning skill. **Never edit another WU's hook file, and never edit
  `operating-rules.md` to add hook behaviour** — add your own file. This is what lets work units run
  in parallel without collision.
- A hook only *notices and offers*. All real work lives in the skill. A hook that contains methodology
  is misplaced.
- Every hook respects the no-nag contract in §5.3.

## 5. The conciseness mandate

### 5.1 Default

EDWIN's default response is **a few sentences at most.** It answers the question asked and stops. No
preamble ("Great question!"), no recap of what the user just said, no summary of what EDWIN is about to
do, no unsolicited caveats, no closing offer of further help unless there is a genuine next step.

### 5.2 Offer, don't deliver

When there is more to say, EDWIN says there is more and waits:

> Three invoices overdue, oldest by 41 days. Want the breakdown?

Not a table of all three with commentary. The user asks if they want it.

### 5.3 No-nag contract

Shared by every hook and every proposal flow (memory, brags, workflow observation):

- **Batch.** Accumulate candidates; raise them together at a natural pause — end of a task, not mid-task.
- **Ask once.** A declined offer is not re-raised for that item, ever. Record a tombstone.
- **Threshold.** Do not raise a batch until it is worth the interruption (≥ 3 candidates, or the task ended).
- **Opt-out.** Honour the relevant `user/config.json` preference without argument or re-litigation.

### 5.4 Exceptions

Long-form output is correct when, and only when:
- The deliverable *is* a document (brag doc, blog draft, briefing, project plan, breakdown file).
- The user asked for depth ("give me the long version", "walk me through it", "explain properly").
- The user's `verbosity` preference is `detailed` — which *relaxes* the default, never removes it.

### 5.5 Applies to

Every skill's dialogue, every example transcript, every prompt EDWIN is instructed to generate, and every
string a script prints. A spec that shows EDWIN being chatty has been written wrong; fix the spec's
example rather than copying it.

## 6. Graceful degradation

Every skill declares, in its `## Degradation` section, what it does when a capability is missing.

| Capability | Present | Absent — required fallback |
|---|---|---|
| Shell / Bash | Invoke the script hook | EDWIN performs the same edit with the harness's file read/write tools, following the file format documented in the skill |
| File tools | Read/write `user/` directly | EDWIN prints the exact content and tells the user where to save it |
| Web search/fetch | Research live | State the limitation, work from provided material, flag what is unverified |
| Scheduling | Register the job | Explain what is unavailable and offer the nearest alternative (calendar reminder with a prepared prompt) |

The canonical fallback ladder is **script → file tools → print-and-instruct**. A skill that stops working
without its script is a defect, not a limitation.

Because of this, every file format under `user/` must be **hand-editable markdown or small JSON** and
documented well enough in the owning skill that the model can maintain it with no script at all.

## 7. Scripts

- **Node ESM only**, `.mjs`, `#!/usr/bin/env node` shebang, **zero runtime dependencies** — stdlib only.
  Anything else (a YAML parser, for instance) is vendored as a small local module with a comment naming
  its scope and limits.
- **Node ≥ 18.** `engines` in `package.json` enforces it; scripts check and exit with a plain-language
  message if the version is lower.
- **Cross-platform, always.** Never concatenate path strings — `path.join` / `path.resolve` only. Never
  assume `/` or `\`. Home directory is `os.homedir()`, never `$HOME` or `%USERPROFILE%` interpolation.
  Never shell out for something Node can do.
- **PowerShell counterparts** (`*.ps1`) exist where the spec calls for a no-Node path. They are allowed
  to be feature-reduced; they must say so when they skip something.
- **Flags.** Every script supports `--help`. Mutating scripts support `--dry-run`. Scripts an agent or
  skill consumes support `--json` emitting a single JSON object on stdout and nothing else (diagnostics
  go to stderr).
- **Exit codes.** `0` success, `1` expected failure with a human-readable message on stderr, `2` bad usage.
- **Never touch `user/`** except the scripts explicitly designed to (`init-user.mjs`, `context.mjs`,
  `memory.mjs`, `brags.mjs`, `register-task.*`). The sync engine creates `user/` and otherwise leaves it
  alone. Nothing ever copies `user/` anywhere.
- **Idempotent.** Running twice does nothing the second time and says so.

## 8. Managed markers

Anything EDWIN writes into a file it does not own is wrapped in markers so the user's own content
survives updates forever. The sync engine only ever rewrites *between* the markers.

```
<!-- EDWIN:BEGIN --> ... <!-- EDWIN:END -->
<!-- EDWIN:MEMORY:BEGIN --> ... <!-- EDWIN:MEMORY:END -->
<!-- EDWIN:CONTEXT:BEGIN --> ... <!-- EDWIN:CONTEXT:END -->
```

Nested sections sit inside `EDWIN:BEGIN`/`END`. If the outer markers are absent, the engine appends a
fresh block; it never rewrites a whole file without `--force`.

## 9. `user/` file schemas

Machine-local, gitignored, never synced, never exported without an explicit opt-in flag. Written by
onboarding (WU-02) and maintained by the owning skills. All are hand-editable by design (§6).

### `user/config.json`

```json
{
  "schemaVersion": 1,
  "name": "Alex",
  "addressAs": "Alex",
  "os": "windows",
  "harness": "claude-code",
  "contextsOwned": ["Work", "Home"],
  "preferences": {
    "verbosity": "concise",
    "memoryCapture": true,
    "bragDetection": true,
    "workflowObservation": true
  },
  "publish": { "remote": "", "branch": "main" },
  "positioning": "",
  "website": "",
  "paths": { "notes": "", "blogDrafts": "", "careerBackground": "" }
}
```

`verbosity`: `concise` (default) | `detailed`. `os`: `windows` | `macos` | `linux`. `harness`:
`claude-code` | `claude-desktop` | `cowork` | `web`. `publish.remote` is the user's *own* repo for
`edwin-publish`; empty means unconfigured and the skill must ask. `positioning` is the free-text goal
used by voice skills such as `x-ghostwriter`; empty means ask at runtime.

`paths` holds optional locations on the user's machine: `notes` (a notes or vault directory),
`blogDrafts` (where drafts are written), `careerBackground` (a CV or similar). `website` is the user's
own site. **Empty is the normal state.** Onboarding does not ask for any of them — a skill asks the
first time it actually needs one, then offers to save the answer. No skill may *require* one of these
to be set; every consumer degrades to working from what the user pastes into the conversation.

**Adding a key.** A skill may not read a config key that is not in this schema. Reading an undeclared
key is a silent no-op: onboarding never writes it, so the branch that consumes it is dead code and the
skill only ever takes its fallback path. If a skill needs new configuration, add it here first, add it
to `tools/sync/init-user.mjs`, and give it a documented default.

### `user/state.json`

```json
{
  "schemaVersion": 1,
  "activeContext": "Global",
  "offTheRecord": false,
  "lastSync": "2026-01-01T00:00:00Z"
}
```

Adding a key is a minor change and needs no `schemaVersion` bump; renaming or removing one does.
Readers must tolerate unknown keys and missing optional keys.

## 10. Ownership, versioning, and changelog

### Shared files — do not edit as a work unit

`CHANGELOG.md`, `package.json`, and `README.md` are **orchestrator-owned**. A work unit that needs an npm
script or a dependency states the need in its completion report; it does not edit the file. This prevents
merge collisions between parallel lanes. Likewise: never edit another work unit's skill, hook file, or
script. Extending a file another WU created (the doctor, the sync engine) happens only when your spec
says so and that WU is complete.

**Agents never run `git` commands.** The orchestrator stages and commits.

### Versioning

- Framework: `core/VERSION`, semver. `0.2.0-dev` during development, `0.2.0` at release.
- Skills: `version` in frontmatter, semver, independent. Patch for wording, minor for new behaviour,
  major for a changed trigger or removed capability. EDWIN bumps this automatically when it edits a skill
  on the user's behalf.

### Changelog

`CHANGELOG.md` follows Keep a Changelog with an `## [Unreleased]` section during development. One bullet
per work unit under the appropriate heading (`Added`/`Changed`/`Removed`/`Fixed`), each ending with the WU
reference: `(WU-05)`.

### Commits

One commit per completed work unit. Subject line: imperative, ≤ 72 chars, prefixed with the WU number.

```
WU-05: add edwin-doctor structure validator
```

## 11. Definition of done

A work unit is complete when:

1. Every acceptance criterion in its spec is satisfied — no scope added, no scope dropped.
2. `npm run doctor` exits 0 (once WU-05 exists).
3. `git grep -inE 'derik|hammer|sqlhammer|C:\\repos|/Users/[a-z]'` finds nothing outside `specs/` and
   `docs/testing/`. Repository URLs in install instructions are the one allowed exception and must be
   the project's own canonical remote, not a personal path.
4. Every new skill has `## Degradation` and `## Examples`, and its dialogue is hyper-concise.
5. Every new script runs on both macOS and Windows path semantics, supports `--help`, and has zero
   dependencies.
6. Discovered gaps outside scope are written up in the completion report for WU-16, not fixed inline.

## 12. Validation

### Running the doctor

```bash
npm run doctor              # Validate entire repo
npm run doctor -- --skill core/skills/<name>   # Single skill
npm run doctor -- --json    # JSON output for tooling
npm run doctor -- --quiet   # Errors only
```

Exit codes: `0` success (warnings allowed), `1` validation failed, `2` bad usage.

### What it checks

| Check group | What it validates |
|---|---|
| **Skills** | Frontmatter present and complete (`name`, `description`, `contexts`, `version`, `requires`, `author`); name is kebab-case and matches directory; description is 40–500 chars with "when to use" signal; contexts exist in `contexts.json`; version is valid semver; required body sections present (`## Purpose`, `## When to use`, `## Instructions`, `## Degradation`, `## Examples`); line count under 250 (warning). |
| **Contexts** | `contexts.json` parses; Global context exists; context names are unique; every context has a description; warns on contexts no skill references. |
| **Persona** | Required files exist (`identity.md`, `operating-rules.md`, `harness-detection.md`); combined line count under 300 (warn) / 400 (error); hook files follow format (`### Hook:`, `**Owner skill:**`, `**Fires when:**`) and stay under 15 lines. |
| **Templates** | Files in `core/templates/` are readable; YAML frontmatter (if present) parses. |
| **Leakage** | Scans `core/`, `tools/`, `docs/`, and root `CLAUDE.md` against `tools/validate/denylist.txt` plus built-in patterns for home paths. Excludes `specs/` and `docs/testing/` from scan. Reports file and line for every hit. |
| **User data** | If `user/config.json` or `user/state.json` exist, validates against §9 schemas (warns on unknown or missing keys; absence is not an error). |

### Extending the doctor

(For WU-17, WU-18, and future work units that add checks)

Checks are registered in a flat array near the top of `edwin-doctor.mjs`. To add a check:

```javascript
// In the checks array:
{
  id: 'memory-digest',           // Unique check ID
  title: 'Memory digest size',   // Human-readable title
  group: 'memory',               // Grouping for output
  run: checkMemoryDigest,        // Function to run
}

// Then implement the check function:
function checkMemoryDigest(ctx) {
  const digestPath = path.join(REPO_ROOT, 'user/memory/digest.md');
  const content = readFile(digestPath);
  if (!content) return; // Absence is OK for user/ files

  const lines = countLines(content);
  if (lines > 60) {
    addFinding('memory-digest', 'error', 'memory', digestPath, null,
      `Digest is ${lines} lines (max 60)`);
  }
}
```

The `ctx` object is shared across all checks and can store data needed by later checks (e.g., `ctx.contextsData` is populated by `contexts-parse` and consumed by skill frontmatter validation).

### JSON output schema

Used by `edwin-setup` (WU-10) and other tooling:

```json
{
  "ok": true,
  "version": "1.0.0",
  "counts": {
    "errors": 0,
    "warnings": 0
  },
  "findings": [
    {
      "id": "skill-frontmatter",
      "level": "error",
      "group": "skills",
      "file": "/path/to/file",
      "line": 42,
      "message": "Missing required frontmatter key: description"
    }
  ]
}
```

`line` may be `null` for file-level findings. `level` is `"error"` or `"warning"`.

### Personal data denylist

`tools/validate/denylist.txt` ships with commented placeholder entries. Users running EDWIN locally should add their own name, paths, and account handles to prevent accidental leakage into committed code.

Entries are case-insensitive substrings or, if wrapped in `/.../`, regular expressions. Lines starting with `#` are comments. The validator also includes built-in patterns for common home directory paths (`/Users/<name>`, `/home/<name>`, `C:\Users\<name>`, drive-letter repo paths).
